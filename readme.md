# Плата наземного приёмника ESP32 + E220

Проект KiCad Rev.1 для несущей платы наземного LoRa-приёмника: съёмный модуль ESP32 DevKit, съёмный EBYTE E220-T22D диапазона 400 или 900 МГц и питание от защищённого двухэлементного литий-ионного аккумулятора. Это инженерный проект реального устройства, а не демонстрационная схема.

## Текущее состояние

Полные и локальные попытки трассировки TPS62133 были корректно отклонены проверяющим: геометрически чистые отдельные фрагменты не складывались в качественную общую силовую ячейку. Активный `hardware/esp32-e220.kicad_pcb` поэтому остаётся историческим рабочим состоянием и **не считается готовым к производству или дальнейшей слепой трассировке**.

Чтобы не менять корпуса компонентов раньше времени, добавлен отдельный безопасный кандидат размещения:

`hardware/esp32-e220-assistant-buck-candidate.kicad_pcb`

Он специально создан без дорожек, переходных отверстий и заливок: **0 tracks / 0 vias / 0 zones**. В нём перемещены только U1/C1/C2/C3/C4/L1 в свободную центральную часть платы. Активная PCB этим файлом не заменена. Кандидат воспроизводится скриптом `hardware/make_assistant_buck_candidate.py`, который отказывается перезаписывать исходную плату. Машинная проверка `check_schematic_pcb_sync.py` дополнена параметром `--pcb`, чтобы проверять такой кандидат без временной подмены активного файла.

Новая физическая политика разделяет питание на два блока:

- J4/F1/D3/Q1/R1/R2 остаются входной защитой возле аккумуляторного разъёма;
- U1/C1/C2/C3/C4/L1 рассматриваются как отдельный компактный остров понижающего преобразователя.

`Q1 → C1` — это подвод `BUCK_IN`, а не локальная высокочастотная петля преобразователя. Его можно сделать длиннее и широким/низкоомным, если локальные `C1 ↔ PVIN/PGND`, `SW → L1`, `L1 → C3`, возврат C3, VOS и SS/TR при этом получаются существенно лучше. Поэтому уменьшение корпусов C1/C2/C3/C4/L1 пока отложено до полноценной проверки нового варианта с текущими деталями.

Координаты, плановые расстояния и обязательный порядок проверки описаны в [assistant-buck-candidate.md](hardware/assistant-buck-candidate.md). В этом окружении native KiCad DRC/ERC не запускались; кандидат должен пройти `check_schematic_pcb_sync.py`, native KiCad DRC, `pcb_routing_planner` на временной копии с реальной медью и затем независимый `pcb_reviewer`. Только после `ROUTING PLAN READY` и reviewer PASS его можно переносить в активную плату.

## Электрическая основа

Активная цепь питания:

`BAT_PLUS → F1 → BAT_FUSED → Q1 → BUCK_IN → TPS62133 → 5V_SYS`.

Защитный ограничитель перенапряжения D3 включён параллельно:

`BAT_FUSED → D3 SMBJ10CA → GND`.

Он не является последовательным элементом. Старые варианты питания несущей платы через USB-C/TUSB320/eFuse отменены и не должны возвращаться в проект.

Машинная проверка соответствия запускается командой:

`python3 hardware/check_schematic_pcb_sync.py --output hardware/esp32-e220-sync-report.json`

Она проверяет 33 схемных устанавливаемых элемента и 33 посадочных места, обозначения, значения, корпуса, соединение площадок с цепями и отсутствие удалённых силовых цепей USB-C. R10 и R11 намеренно имеют состояния `DNP` и `NO_FOOTPRINT_DNP`.

## Ограничения следующего этапа

До нового решения проверяющего нельзя начинать трассировку за пределами местной силовой ячейки.

Расчётные правила при предположении наружной меди 1 унция/фут²:

- сигнальные дорожки: предпочтительно 0,25 мм, минимум 0,20 мм в тесных местах, зазор 0,20 мм, переходное отверстие 0,60/0,30 мм;
- силовые цепи `BAT_PLUS`, `BAT_FUSED`, `BUCK_IN` и основная `5V_SYS`: предпочтительно 1,0 мм; обоснованные местные ответвления `5V_SYS` могут иметь ширину 0,8 мм;
- `BUCK_SW`: только короткий участок верхнего слоя, без переходных отверстий, с минимальной практически необходимой площадью меди.

Масса меди остаётся производственным допущением и должна быть подтверждена перед выпуском.

D2 имеет статус `PLACEMENT_CANDIDATE_NOT_RELEASED`: посадочное место WS2812 не разрешено для производства, зависимые от него соединения пока не трассируются. Механическая привязка OLED также остаётся отложенным вопросом.

## Структура проекта

- `hardware/esp32-e220.kicad_sch` — утверждённая электрическая схема.
- `hardware/esp32-e220.kicad_pcb` — текущее частично разведённое состояние платы без глобальных заливок.
- `hardware/generate_esp32_e220.py` — воспроизводимый исходник схемы.
- `hardware/generate_stage7_footprints.py` — воспроизводимый исходник библиотеки посадочных мест.
- `hardware/generate_stage8_placement.py` — генератор исходного размещения; его нельзя использовать для полного сброса платы без прямого разрешения.
- `hardware/check_schematic_pcb_sync.py` — машинная проверка соответствия схемы и платы.
- `hardware/esp32-e220-power-routing-report.md` — англоязычный отчёт, предназначенный для агентов.
- `docs/agent-context.md` — краткий англоязычный рабочий контекст агентов.
- `AGENTS.md` и `.codex/agents/` — англоязычные правила и профили агентов.
- остальные файлы `docs/*.md` — русскоязычная документация для человека.

## Языковое правило

Файлы, которые читают или создают агенты как инструкции, доказательства, отчёты или машинные исходники, ведутся на английском языке. Документация для человека, не входящая в рабочий контекст агентов, ведётся преимущественно на русском. Обозначения элементов, номера деталей, имена цепей, выводов, файлов, команд, единицы измерения и фиксированные статусы не переводятся.

Критические параметры, распиновки, корпуса и требования по радиочастотной части подтверждаются официальными документами изготовителей. Подробная человеческая история решений хранится в каталоге `docs/`.
